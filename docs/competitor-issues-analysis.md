### 这张表最重要的三个结论

**① 星数跟代码量基本无关。**

- `alisamsam`：**83 KB、22 个 py、只有 1 个测试文件**，拿到 **189 星**
- `andrewbartels1`：**43 MB、308 个 py、174 个测试**，只有 **91 星**

差了 500 倍体积，星数反而少一半。**说明星数不来自工程量。**

**② 星数也不来自测试覆盖率。**

`eyfel`（SolidPilot）测试密度只有 **0.24**，比 swforge 的 0.38 还低，却有 **458 星**。
它的星来自**一个足够硬、足够新的想法**：把 DXF 图纸反向重建成实体零件，9 张真实图纸核对到 0.02%。

**③ 星数来自「一句话能说清的价值」+「一眼能看懂的证据」。**

- wzyn：*"Tool success is not task success"* + GIF 动图 + 1045 项测试
- eyfel：*"把供应商发来的 DWG 变成可建模的实体"* + 0.02% 精度证据
- alisamsam：*"22 tools for parts, sketches & features"* + 干净的 README

**swforge 现在缺的正是这个**：没有一句话能说清的独特价值，也没有一张动图。

>

**这一节的说服力比任何功能列表都强**，因为它引用了别人仓库里的真实编号。

## 四、尺寸过度标注：技术方案

### 现状（实测）

```
INS_DIMS(8)           →  0 个
MARKED(32768)         → 22 个
NOT_MARKED(524288)    →  0 个
全部组合              → 22 个
```

**不管怎么选类型，都是 22 个。** 所以问题不是类型选错，而是
`InsertModelAnnotations4` 自己摆放时**不做避让**，把 11 个尺寸全堆在视图同一边。

### 方案 A：移动已有尺寸（需要 C#）

实测 `DisplayDimension.GetAnnotation()` 在 pywin32 下报「找不到成员」，
和面/顶点/`IFace2.GetSurface` 是同一类限制，**必须走 C#**。

算法：读每个尺寸相对视图中心的位置，按角度分桶，同一角度桶内的尺寸
按半径依次外推，保证间距 ≥ 8 mm。

**风险**：角度分桶在尺寸挤在一侧时会推得很远，可能超出图框。

### 方案 B：不铺量，只标该标的（推荐）

不再无脑 `InsertModelAnnotations4`，改成**受控标注清单**：

- 每个视图必标：总长 / 总宽 / 总高（`dims.py` 已实现，实测 160/140 正确）
- 按需标：孔位、板厚、管壁厚 —— 由调用方指定，工具只负责建和摆

好处：
- 尺寸数量从 22 降到 6~10
- 每个尺寸位置由我们决定，天然不重叠
- 符合本项目「不编造、可交付」的原则 —— 铺满一屏尺寸反而是不可用的图

### 方案 C：两者结合（最终方案）

```
add_dimensions(
    drawing,
    curated=True,        # 默认：只标总尺寸 + 关键特征
    blanket=False,       # 可选：保留原来的铺量行为（老的调用方兼容）
    spread=True,         # 铺量时做一轮外推避让
)
```
