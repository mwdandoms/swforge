## 二、为什么 v1.2 该做什么（按证据排）

下面每一项都有依据，不是凭感觉。

### 1. 完整验证 BOM 的实机路径 ⭐ 最高优先

**依据**：`InsertBomTable6` 有 12 个参数，`GetMaterialUserName` 的真实返回值
还没在真机上确认过。**未验证的功能不能对外宣称可用。**

这是 v1.1 留下的硬缺口。必须先做完。

---

### 2. SolidWorks 版本兼容矩阵

**依据**：竞品 issue 里这是高频问题 ——
- hjbaard #2「Compatibility: SOLIDWORKS 2026 SP4.1」
- eyfel #12「SolidWorks 2026 SP4 crashes during sketch creation」
- vespo92 #6「Windows 11 issue」

**现状**：只在 SW 2025 SP5.0 上测过。README 写的是「2025 SP5 tested」，
其他版本一句「未测试」带过。

**该做什么**：
- `swforge selftest` 已经是版本无关的，换个版本跑一遍就知道哪里坏
- 把结果整理成兼容矩阵表
- 关键 API 做降级路径（比如 `InsertBomTable6` 不存在时回退到 `InsertBomTable3`）

**难度**：中。真正的成本是**需要多台机器或虚拟机**，不是代码。

---

### 3. 公差与粗糙度标注

**依据**：这是 README 里明确承认没做的第一项，也是用户最可能失望的地方。
一份「GB 标准工程图」缺了公差和粗糙度，实际上不能交付。

**现状**：`docs/limitations.md` 写着「不生成，需人工补」。

**该做什么**：分两步
- **第一步**：从建模时记录的公差信息生成标注（可控，有数据来源）
- **第二步**：不做「自动推荐公差」——那需要工艺知识，做不好就是害人

**难度**：高。这是 v1.2 里最硬的一块。

---

### 4. 多客户端并发的实机验证

**依据**：守卫代码写了，但只在「同一进程内模拟抢占」验证过。
**真正的两个进程同时操作还没测。**

**该做什么**：写一个双进程测试：
```
进程 A: 循环激活文档 A 并建模
进程 B: 循环激活文档 B 并建模
断言: 两边的结果都正确，或者至少能明确报错而不是静默出错
```

**难度**：中。难点在测试稳定性，不在实现。

---

### 5. 装配级干涉的独立验证

**依据**：本项目 `body_interference`（单零件多实体）和
`check_interference`（装配）是两条不同路径，后者刚修好明细为空的问题。

**该做什么**：用更复杂的装配（3 个以上零件、部分接触部分相交）
验证干涉数量和体积都对得上手算值。

**难度**：低。

## 三、明确**不做**的事

写下来是为了避免以后反复讨论。

| 不做 | 为什么 |
|---|---|
| **通用几何内核** | 那是 OpenCascade / Parasolid 的领域，不是本项目定位 |
| **替代工程师判断** | 公差、材料、工艺选型需要人的判断，工具只做「把验证做到工具层面」 |
| **跨平台** | SolidWorks 只有 Windows 版，支持 macOS 是伪需求 |
| **完整 Mock 适配层** | 生成源码快照测试已经拿到 70% 收益，成本 1/5。完整 Mock 等有外部贡献者时再做 |
| **自动推荐设计方案** | 做不好会误导，而且没有任何验证手段能证明「推荐得对」 |

## 四、关于「传播」的判断

竞品数据显示（详见 `competitor-issues-analysis.md`）：

```
alisamsam     83 KB,  1 个测试文件   → 189 星
andrewbartels1 43 MB, 174 个测试文件  →  91 星
eyfel         14 MB,  7 个测试文件   → 458 星
```

**差 500 倍体积，星数反而少一半。说明星数不来自工程量。**

那么来自什么？三个案例的共同点：

1. **一句话能说清的、别人没解决的痛点**
2. **一眼能看懂的证据**（GIF / 精度数字 / 对比表）

**据此的判断**：

| 该做 | 不该做 |
|---|---|
| 一段 30 秒的实机演示 GIF | 再写一万行功能 |
| `selftest` 输出截图当证据 | 更多没人看的文档 |
| 一句话定位（「不确定结果对不对的自动化，不算自动化」） | 更长的功能列表 |

**这个判断可以错。** 如果 v1.2 发出去之后半年还是 0 星，
那说明问题不在工程量也不在表达，而在**这个需求本身不够痛**。
那时候该考虑的不是继续加功能，而是换方向。

## 五、下一个月的具体动作

```
第 1 周   BOM 实机验证 + 修问题（这是硬缺口）
第 2 周   版本兼容矩阵（至少测 SW 2024 / 2025 / 2026）
第 3 周   公差标注第一步（从建模数据生成，不做自动推荐）
第 4 周   双进程并发测试 + 复杂装配干涉验证
```

**每个周末必须有可验证的产出**，宁可少做也不做没验证的东西。

## 六、什么情况下该停下来

提前定好退出条件，避免无限投入：

| 信号 | 含义 |
|---|---|
| 连续两个版本没人提 issue | 要么没人用，要么用了没问题——先搞清楚是哪个 |
| 用户反馈集中在「不如手点」 | 说明自动化没带来净收益，方向有问题 |
| 维护成本超过每周 4 小时 | 个人项目撑不住，要么砍功能要么找人 |

**这些不是丧气话，是让项目能持续的标准。**
